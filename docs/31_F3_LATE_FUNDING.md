## 1. Current semantics (from the code at `main` = `2ccd058`)
- **Creation** (`terms.rs` `validate`, lines ~310–357): `now < acceptance_deadline_ns`; `funding_deadline_ns ≥ acceptance_deadline_ns`; per line `delivery_deadline_ns ≥ funding_deadline_ns` (**equality allowed**); `delivery_grace_period_ns ∈ [0, 30 d]` (**0 allowed**); windows ∈ [60 s, 30 d]; phase sums bounded (`PhaseScheduleOverflow`).
- **Funding** (`line.rs` `fund`, line 528; `deadlines::funding_open`): allowed iff the line is UNFUNDED, the agreement is AGREED/ACTIVE, `now < funding_deadline_ns` and the amount is exact. **No reference to the line's delivery deadline.**
- **Submission** (`line.rs` `submit_delivery`): allowed iff FUNDED and `now < delivery_deadline_ns + grace` (`submission_open`). At equality NON_DELIVERY becomes eligible with T0 = delivery + grace.
- **Consequence:** terms with `delivery_deadline == funding_deadline` and grace 0, funded at `funding_deadline − 1 ns`, leave the supplier **1 ns** to submit; the line then goes NON_DELIVERY → arbitration/fallback. Funds are never stolen (allocation still needs a ruling, a mutual split or the signed fallback), but a supplier who worked off-chain on trust can be forced into a dispute. Any gap smaller than the real work time has the same effect in degree.
- **Rejected deposits today:** `ft_on_transfer` → `try_credit_deposit` works on a copy; any error returns `Err(code)` before anything is written; `ft_on_transfer` returns the **full amount** (`PromiseOrValue::Value(amount)`) and logs `LF_FT_REFUND:<code>`; the pinned token's `ft_resolve_transfer` refunds the sender; `custody_total` (E) is untouched (Rule B: checked add only after all checks). Verified by LF-005 tests T019–T035, T057, T066.

## 2. Two minimal remediation options (both keep the terms serialization and hash v1)
**Common definition:** for line *i*, `submission_cutoff_i = delivery_deadline_ns(i) + delivery_grace_period_ns` (existing). Minimum delivery time **D = `review_window_ns`** (already signed, ∈ [60 s, 30 d], default 72 h): the supplier is guaranteed at least as long to deliver as the buyer has to review. No new field, no new constant.

## 3. Recommendation
**Option A** as the smallest safe change: one runtime condition plus one error code, no change to the terms schema, hash, validation, shared vectors or TS encoder, no stored-state change, and late deposits use the already-verified full-refund path with zero liability. Option B is stricter UX but changes the frozen validation surface (the golden vector would no longer validate), which is a larger compatibility change than F3 warrants for the hackathon.
Open question for the founder: **D = `review_window_ns`** (recommended: signed, symmetric) or a contract constant (e.g. 60 s minimum, which only removes the 1-ns degenerate case).

## 4. Compatibility impact of Option A
- Signed terms, canonical encoding, hash v1, stored `LineStateV1` / root layout: **unchanged**.
- Contract version string changes; release WASM hash changes; new ABI-visible error code (`ERR_LINE:DeliveryTimeTooShort` from direct paths is not reachable — funding only happens via `ft_on_transfer`, so it appears as the refund log code `LF_FT_REFUND:DeliveryTimeTooShort`).
- S6 oracle: the Fund prediction must include the new rule (otherwise oracle mismatch — this is how the harness will prove it).
- Existing tests: accelerated timings fund well before `submission_cutoff − review` (e.g. `short_timing`: delivery +90 s, review 60 s ⇒ funding must happen by +30 s; it happens within seconds of acceptance) — to be confirmed by the full suite.
- Frontend: new derived value per line; no fixture/vector change beyond the ABI version.

## 5. Tests (written before code, on approval)
Unit: boundary at `submission_cutoff − D − 1` (accepted), `= submission_cutoff − D` (accepted, equality), `+ 1` (rejected `DeliveryTimeTooShort`); interaction with `funding_deadline` (whichever is earlier binds; both orders); grace > 0 extends the cutoff; checked-add overflow path (unreachable under creation bounds, still rejected); rejected funding leaves line, agreement, E byte-identical. Property (S6): Fund oracle includes the rule; boundary tags `funding_delivery_gap_{minus1,exact,plus1}` with ok-count assertions. Genuine-token sandbox: late deposit after the effective cutoff → `used == 0`, buyer balance unchanged, escrow balance unchanged, E unchanged, log `LF_FT_REFUND:DeliveryTimeTooShort`, line UNFUNDED; on-time deposit succeeds; E2E lifecycle unchanged. Adversarial: deposit in the same block as the cutoff; repeated late deposits; deposit for another line of the same agreement still accepted. Mutation: condition removed; `<` vs `≤`; D replaced by 0; grace ignored.

## Approved rule (frozen before coding, 2026-11-05)
For line *i*, a deposit through `ft_on_transfer` is credited iff all existing checks pass **and** `now_ns + review_window_ns ≤ delivery_deadline_ns(i) + delivery_grace_period_ns`, evaluated with checked u64 arithmetic: if `now + review_window` overflows u64 the deposit is rejected; `delivery + grace` cannot overflow (creation-time `SubmissionCutoffOverflow` / `PhaseScheduleOverflow`) and is still computed checked. Equality is accepted (the supplier has exactly D). Check order in `fund`: line UNFUNDED → `now < funding_deadline` → **delivery-time rule** → exact amount. Rejection code `DeliveryTimeTooShort`, surfaced as `LF_FT_REFUND:DeliveryTimeTooShort`; the full amount is returned, nothing is written, `custody_total` unchanged. Deadlines, grace, T0 derivations, terms encoding/hash, validation, stored layout: unchanged. Policy match (founder): rejects funding when the remaining time before the agreed delivery cutoff is less than D; preserves the agreed deadline; no liability for rejected deposits.

**Zero `review_window_ns` is not permitted.** Creation-time validation (`terms.rs`, `MIN_WINDOW_NS..=MAX_WINDOW_NS`, i.e. 60 s … 30 d) rejects 0 and anything below 60 s (`TermsError` window range; tests `terms::…` bad values `[0, MIN−1, MAX+1, u64::MAX]` and contract-level `f3_review_window_cannot_be_zero_or_below_minimum`). So the F3 guard can never degenerate to "no minimum". **Disclosed limitation:** F3's protection equals the signed review window, so terms signed with the 60 s minimum review window guarantee the supplier only 60 s of delivery time after funding. F3 removes the 1-ns trap and ties delivery time to a value the supplier explicitly accepted; it does not judge whether a signed window is commercially adequate (the UI should show the effective funding cutoff and warn on short windows).

**Version string:** the qualified build reports `linefair-escrow 0.1.0 (lf-012 f3)` (with a space). Changing it to any other spelling (e.g. `(lf-012f3)`) changes the WASM hash and would require full re-qualification; the string is therefore left as qualified.
