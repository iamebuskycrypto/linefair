## 2. Exact preimage layout (`docs/20` §Preimage, `hash.rs::terms_preimage`)
```text
"linefair/agreement/v1"           21 ASCII bytes, no length prefix
0x00                              1 byte
bstr(network_id)                  "sandbox" | "testnet"
bstr(escrow_contract_id)
Borsh(AgreementTermsV1):
  schema_version            u16 LE
  deadline_rules_version    u16 LE
  buyer_id                  bstr
  supplier_id               bstr
  primary_arbitrator_id     bstr
  backup_arbitrator_id      bstr
  ft_contract_id            bstr
  agreement_nonce           u64 LE
  acceptance_deadline_ns    u64 LE
  funding_deadline_ns       u64 LE
  delivery_grace_period_ns  u64 LE
  review_window_ns          u64 LE
  negotiation_window_ns     u64 LE
  primary_window_ns         u64 LE
  backup_window_ns          u64 LE
  lines                     u32 LE count, then per line:
    line_id                       u32 LE
    principal                     u128 LE (16 bytes)
    delivery_deadline_ns          u64 LE
    acceptance_criteria_commitment [u8;32] raw, no prefix
    fallback_buyer_bps            u16 LE
    fallback_supplier_bps         u16 LE
bstr(x) = u32 LE byte length || UTF-8 bytes
digest  = SHA-256(preimage), rendered as 64 lowercase hex
```
`terms_hash`, `agreement_id`, acceptance flags and runtime state are not in the preimage. Encoding writes whatever the struct holds: it does not validate. A line count of 0 or 4 still encodes, because only validation rejects it.

## 3. Strict JSON-edge parsing (`docs/20` §JSON edge; `terms_json.rs`; `schemas/agreement-terms-v1.schema.json`)
`JSON.parse` must **not** be used for terms, for three reasons: (a) it silently keeps the last of duplicate keys (Rust: `Json`); (b) it cannot distinguish `5000` from `5000.0` or `5e3` (Rust: `Json` for a float into u16/u32); (c) it accepts lone UTF-16 surrogate escapes that serde_json rejects. The plan is a small custom tokenizer/parser (proposal: hand-written, no dependency) that keeps the **lexeme** of every number and detects duplicate keys per object.

Rules, mirroring serde derive with `deny_unknown_fields` (stage `parse`):
| Input | Rule | Code |
|---|---|---|
| Whole text | Exactly one JSON value, an **object**; RFC 8259 whitespace allowed around it; trailing non-whitespace, empty input, top-level array → reject | `Json` |
| Keys | Exactly the 16 top-level and 6 per-line keys; unknown, missing or duplicate → reject; key order is free | `Json` |
| `null` anywhere a value is required | reject | `Json` |
| `schema_version`, `deadline_rules_version`, `fallback_*_bps` | JSON **integer** lexeme (no `.`, no exponent, no sign other than leading `-`) in 0..=65535; a string, float, negative or out-of-range → reject | `Json` |
| `line_id` | JSON integer lexeme in 0..=4294967295; negative → reject | `Json` |
| u64 / u128 fields (`agreement_nonce`, all `*_ns`, `principal`) | Must be a JSON **string** (a number → `Json`); content `^(0|[1-9][0-9]*)$` else `NonCanonicalDecimal`; value ≤ 2⁶⁴−1 / 2¹²⁸−1 (BigInt compare) else `DecimalOverflow` | as stated |
| Account ids (5 fields) | near-account-id 2.6.0: byte length 2..=64; chars `[a-z0-9]` or separators `-_.`; no leading, trailing or consecutive separators | `InvalidAccountId` |
| `acceptance_criteria_commitment` | exactly 64 chars `[0-9a-f]` | `InvalidCommitmentHex` |
| `lines` | JSON array of objects; any length (count is checked in validate) | `Json` if not an array |

**Error precedence must match Rust.** serde reports any `Json` error before the field conversions run. Then `TryFrom` converts in a fixed order: `buyer_id`, `supplier_id`, `primary_arbitrator_id`, `backup_arbitrator_id`, `ft_contract_id`, `agreement_nonce`, `acceptance_deadline_ns`, `funding_deadline_ns`, `delivery_grace_period_ns`, `review_window_ns`, `negotiation_window_ns`, `primary_window_ns`, `backup_window_ns`, then for each line in array order `principal`, `delivery_deadline_ns`, `acceptance_criteria_commitment`. The first failure wins. The TS parser therefore runs in two passes: a structural/type pass (→ `Json`), then a conversion pass in this order.

Edge behaviour that the current vectors **do not** pin down, and that must be resolved by adding Rust-generated cases (a later Rust-side change, not done here) before TS relies on it: `-0` and `1e2`/`1E2` for integer fields; `\u`-escaped account-id characters (serde decodes them before the AccountId check); lone surrogates; a leading UTF-8 BOM; leading `+`/`.5` lexemes (invalid JSON anyway); deep nesting limits; which error wins when a document has both a duplicate key and a type error. Until those cases exist, the TS parser takes the stricter choice (reject) and the item stays open.

## 4. Arithmetic
- All u64/u128 values are `bigint` from parsing to encoding. `Number` is forbidden for them. Lint rule (proposal): no `Number(`, `parseInt`, `parseFloat` or unary `+` in `src/terms/`. u16/u32 fields are JSON integers that may be range-checked as `number` after the lexeme check, because every value ≤ 2³²−1 is exact.
- LE encoding is written by hand: `DataView.setUint16/32(…, true)` for u16/u32 and `setBigUint64(…, true)` for u64; u128 is written as two `setBigUint64` calls (low then high) or as 16 bytes via `& 0xffn` shifts. A range assertion runs before writing.
- Checked sums use BigInt and compare against `2n**64n - 1n` / `2n**128n - 1n`. No wraparound is allowed.

## 5. Cross-field validation (stage `validate`; `terms.rs::validate`, exact order)
Context = `context` from the vectors (in the app: `get_config` plus the latest block time).
1. `schema_version == 1` else `UnsupportedSchemaVersion`
2. `deadline_rules_version == 1` else `UnsupportedDeadlineRulesVersion`
3. `ft_contract_id == allowlisted_ft_id` else `FtNotAllowlisted`
4. the 4 roles (buyer, supplier, primary, backup) pairwise distinct, else `RolesNotDistinct`
5. no role equals escrow, FT or operator treasury, else `RoleIsReservedAccount`
6. `now_ns < acceptance_deadline_ns` else `AcceptanceDeadlineNotInFuture`
7. `funding_deadline_ns >= acceptance_deadline_ns` else `FundingDeadlineBeforeAcceptance`
8. `delivery_grace_period_ns <= 2 592 000 000 000 000` else `DeliveryGraceOutOfRange`
9. each window (review, negotiation, primary, backup, in that order) in `[60 000 000 000, 2 592 000 000 000 000]` else `WindowOutOfRange`
10. `1 <= lines.length <= 3` else `LineCountOutOfRange`
11. for each line, in order: `line_id == index` (`LineIdMismatch`), `principal > 0` (`ZeroPrincipal`), both bps ≤ 10 000 (`BpsOutOfRange`), sum == 10 000 (`BpsSumInvalid`), `delivery_deadline_ns >= funding_deadline_ns` (`DeliveryDeadlineBeforeFunding`), `delivery + grace` fits u64 (`SubmissionCutoffOverflow`), `cutoff + review + negotiation + primary + backup` fits u64, as a checked fold (`PhaseScheduleOverflow`)
12. **Rule A** (`docs/07` §APPROVED and IMPLEMENTED): Σ principal over all lines fits u128 (checked fold), else `PrincipalSumOverflow`. It runs after every per-line rule.

Derived (not hashed): `accelerated_test_timing` = any of the four windows below its default (72 h / 48 h / 72 h / 72 h). TS must match the `accelerated_test_timing` field of each vector.

## 7. Three-way agreement: Rust ↔ TS ↔ Python
- **Rust** (reference): `terms_vectors.rs` generates the file and checks it against the public API.
- **Python** (`evidence/m1/s2-independent-encoder-check.py`, stdlib only; run as `python3 -I evidence/m1/s2-independent-encoder-check.py packages/shared-schemas/vectors/terms_v1.json`): re-encodes golden, identical_preimage, field_mutations, reordered_lines, binding and json_equivalence. It does **not** check account ids, validation or the malformed cases, and it uses `json.loads` (which keeps duplicate keys). So the three-way check covers **encoding only**. Malformed parity is **Rust ↔ TS**.
- **Check (TS-22):** a script loads the vector file once and records `(section, index, label, digest)` from TS and from Python (its output, or a small wrapper that imports nothing new). It asserts that all three sources agree on all 31 hashed vectors (1 + 1 + 22 + 2 + 3 + 2) and that the golden digest is printed by all three. The Python file is not modified. If it needs a machine-readable output mode, that is a separate approved change.

## 8. Sandbox check against `compute_terms_hash` (TS-23)
`compute_terms_hash(terms)` is a view that parses and hashes without validation (`lib.rs`). It uses the contract's own `network_id` and `env::current_account_id()`.
1. Deploy the recorded escrow WASM into the local sandbox (pinned `near-sandbox` 2.13.4, `NEAR_SANDBOX_BIN_PATH`, `docs/21`), initialised with `network_id = "sandbox"`.
2. For the golden terms and each mutation/reordered vector: TS digest computed with `(network="sandbox", escrow_id=<sandbox escrow account>)` == `compute_terms_hash(terms)`.
3. `create_agreement` with valid terms (deadlines shifted to the sandbox clock and the FT/treasury ids replaced). Then `get_agreement(id).terms_hash` == TS digest of `get_agreement(id).terms` == `compute_terms_hash`.
4. Every malformed `parse`-stage case sent to `compute_terms_hash` fails with `ERR_TERMS_PARSE:<code>` equal to the TS code. Validate-stage cases sent to `create_agreement` fail with `ERR_TERMS_INVALID:<code>`, except where the contract's context differs from the vector context (e.g. `now`, FT id). Those cases are rebuilt for the sandbox context and say so.
5. Save the log under `evidence/` with the commit SHA, WASM sha256, sandbox binary sha256 and exit code (`docs/18` template). Testnet repetition happens only at LF-014 with founder approval.

Driver choice (near-workspaces from Rust, a JS RPC client, or near-cli-rs) is PENDING. near-cli-rs 0.30.1 is not installed and needs founder approval (`docs/21`).

## 10. Library choices (all proposals, pending verification)
- SHA-256: WebCrypto in the browser, `node:crypto` in tests. Both are built in.
- Borsh: no library proposed. The layout is fixed and small. If a library is ever adopted, its output must still pass TS-02…TS-12 byte for byte, and its exact version must be pinned.
- JSON: custom strict parser. A third-party "strict JSON" parser is a proposal only if it provides lexeme preservation, duplicate-key errors and surrogate validation, and it must pass TS-13…TS-16.
